# Bugs and mitigations

The catalogue the rewrite works from, with one row per problem found in the audit.

- **Severity:** Critical, High, Medium or Low.
- **Port action:**
  - `keep for parity`: the new dashboard reproduces this on purpose. The Mitigation column gives the reason.
  - `fix in the new app`: a presentation-layer problem the new app designs out. The Mitigation column says how.
  - `out of scope`: a backend problem, recorded here but not changed by this project.
- When a slice resolves a row, wrap its Citation in `~~` and add *(Resolved in slice NN-NN-NN, YYYY-MM-DD.)* to the Mitigation. Never delete rows.
- Never put a literal pipe character in a cell.

## Gate 2 decisions (2026-09-26, user)

- **Header:** add sex (Patient.gender) and a status of "Deceased (date)" when Patient.deceasedDateTime is present, otherwise "Active". Patient.active is never read (BM-005). The first answer was "sex only"; the user revised it to add status so the challenge requirement is met.
- **Data source:** FHIR only, with safe workarounds. The Standard REST API is not used for any clinical card. *Amended 2026-09-26 (user decisions after the Codex, Fable and Opus parity reviews):* the Medications card is built from the Standard REST API medication list and the Allergies card reads each allergy's title, end date and outcome from the Standard REST API, because FHIR gets both wrong (BM-044, BM-047); and staff and facility names are read with a server-only system client, because OpenEMR's API lets only administrators read them (BM-048). The Medical Problems card is built from the Standard REST API problem list, the old card's own source, because FHIR leaves problems out (BM-051).
- **Medications and Prescriptions:** two cards, split on intent, with the caveat documented (BM-019, BM-020). Superseded 2026-09-26: split by membership of the standard API medication list, so both cards match the old ones (BM-019).
- **Problem list:** every problem that is not inactive, with resolved and recurrence labelled (BM-017). Superseded 2026-09-26: the card now applies the old rule to the standard API problem list (BM-051).
- **Allergy severity:** FHIR risk level, with high highlighted (BM-011).
- **Empty allergy list:** "No allergies recorded", never "No Known Allergies" (BM-012).
- **Names FHIR can't resolve:** shown as "Name unavailable" (BM-028, BM-032). Staff and facility names are read with a server-only client so non-admin users see them too (BM-048, 2026-09-26).
- **Keep for parity:** BM-014 (entry order, high highlighted), BM-016 (future end-date allergy hidden; superseded 2026-09-26, now shown via the Standard REST API), BM-018 (oldest start date first) and BM-034 (newest 20 visits plus "Show all").
- **Codex parity review follow-ups (2026-09-26):** refills show "Not available" (BM-041); prescription permissions stay as OpenEMR's API enforces them (BM-042); a medication with a future end date must not be treated as finished (BM-044), done for the medication list by reading its end dates from the Standard REST API.
- **Hidden cards:** the new app reads a list of hidden cards from its own configuration file, mirroring `hide_dashboard_cards`. Per-user permissions are enforced by OpenEMR's API through the login scopes.
