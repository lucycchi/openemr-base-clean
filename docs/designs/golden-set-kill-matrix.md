## Problem Statement

The Week 2 PRD asks for "a 50-case golden set with boolean rubrics" and a
PR-blocking hook that fails "if any category regresses by more than 5% or
drops below the pass threshold". The hard gate: "During grading, we will
introduce a small regression and confirm your CI gate fails."

The golden set already exceeds the count: 70 cases in `tests/evals/cases/`,
54 deterministic (run by the pre-push hook with no API key) and 16 live.
All five PRD rubrics are scored on a plain push (`no_phi_in_logs` since
f261078), any deterministic pass-to-fail flip fails the gate (e8737cb), and
`clinical_copilot_week2/EVAL_DATASET.md` §3 states there is no LLM judge.

What is not known is the thing the graders will test: **for a small code
regression a grader might plausibly inject, does a plain `git push` refuse
it?** The self-test (`gate.php --self-test`, lines 130-156) flips a recorded
verdict. It proves the comparison logic, not that any case catches a real
code change. The only recorded code-level proof is one manual mutation of
`Verifier.php` (tests/evals/README.md, "Recorded proof").

**"Plain push"** in this document means the installed pre-push hook chain
exactly as `tests/evals/gate.sh pre-push` runs it with no API key: sidecar
pytest, then `case-index.php --check`, then the module's isolated PHPUnit
suite, then `gate.php` over the deterministic cases (gate.sh lines 80-96).

Three holes are confirmed in the code today. The third was found by the
spec review (R2-1) and is the widest:

0. **A Python edit is not tested unless the sidecar image is rebuilt.** The
   sidecar's code is baked into its image (`docker-compose.yml` `build:`;
   the only volumes are read-only `contracts/` and `tests/evals/fixtures`),
   and nothing in `gate.sh` rebuilds or checks it. A grader who edits
   `anchor.py`, `graph.py`, `retrieve.py`, `schemas.py` or `llm.py` and runs
   `git push` gets pytest and the sidecar golden cases run against the old
   code, and the push passes. Every Python layer is exposed.

1. **PHI on the brief and ask paths is live-only.** Deterministic PHI cases
   69 and 70 drive upload, extract and list only. `phi.php` can drive
   `ChatController` brief and ask (lines 157-167), but the cases that do
   (38 question logs, 68 plan-note logs) are `live: true`. A line such as
   `$this->logger->info('ask: ' . $question)` in `ChatController` is expected
   to pass a plain push (Next Steps 1 confirms). A runtime log-field
   allowlist (T7.3, `LogFields`, being built in another session) will drop
   values under unknown keys, but not PHI placed in the message text or under
   an allowlisted key, so the hole stays open after T7.3.
2. **Prompt edits are invisible without a key.** Deterministic cases replay
   recorded model replies, and nothing fingerprints the prompt text in
   `src/Prompt.php` (`VERSION = '2026-09-23.1'`) or the strings in
   `sidecar/copilot_sidecar/llm.py` (`PROMPT_VERSION = "2026-09-21.1"`).
   Deleting the "cite every sentence" rule is expected to pass a plain push.

## What Makes This Cool

A committed table: "N regressions of the kind a grader would inject, across
nine layers; this many were refused by the plain push on the first run,
this many after the fixes; here is the stage, rubric and case that caught
each." It turns "we believe the gate works" into evidence that can be
re-run, and it is the best answer to the interview question "how do you
know your evals catch regressions?"

### Part 0: the hook tests the code being pushed (hole 0)

`/health` gains `source_sha256`: a hash over the sidecar's
`copilot_sidecar/*.py` and `tests/*.py`, computed once at start-up.
`gate.sh`, before its pytest stage, computes the same hash over the checkout
and compares. On a mismatch it rebuilds and restarts the sidecar of the same
compose project (`docker compose -p <project> build copilot-sidecar` then
`up -d copilot-sidecar`, from the project's `working_dir` label; cached
layers keep this to tens of seconds), waits on `/health`, and compares
again. A second mismatch refuses the push (fail closed) with
`sidecar image does not match the checkout`. The matrix uses exactly this
path for Python mutants, so what the matrix measures is what a grader's push
runs. This comes first in the build order.

### Part 1: close the two remaining known holes

**F1. Deterministic PHI twins for brief and ask.** Two new cases, siblings of
38 and 68 without `live`: the real `ChatController` brief and ask on a
throwaway patient, every model and sidecar call replayed.

Checked on 2026-09-23: `ChatController` has no model seam. Its constructor
takes logger, request, `Config`, tracer and receipts; the narration pipeline
is wired by `BriefingPipelineFactory`; `Config` has no OpenAI base URL;
`brief()` and `ask()` return early when `!$config->hasOpenAi()` (lines 317,
431); and the sidecar is reached statically,
`SidecarClient::fromConfig($config)->brief(...)` (line 380) and
`->answer(...)` (line 443, which carries the question text).

F1 therefore adds two optional constructor arguments to `ChatController`,
each defaulting to today's wiring: the chat-completion client used by the
narration pipeline, and a `SidecarClient` (as `DocumentController` already
accepts one). `phi.php` builds all three together in one helper: a `Config`
whose `hasOpenAi()` is true because it carries the placeholder key
`eval-replay-no-network`, a replaying chat client that reads the case's
recorded narration and never opens a socket, and a `SidecarClient` pointed at
the test-only `/eval/run-recorded` endpoint (f261078). Today that endpoint
takes only an extraction proposal and runs brief mode with stub retrieval and
answer mode with no chunks; F1 extends it with an optional per-mode
`recorded_chunks` field so brief and answer return fixed evidence without an
embedding or rerank call, whatever keys the sidecar holds, and has it return
the log lines it emitted for the request it served (captured in-process, as
`/eval/phi` does for its own call), so `phi.php` can scan them without a
docker CLI. Because the placeholder key exists only inside that
helper and is paired there with the replaying client, it cannot reach a real
HTTP call. No `new` inside business logic, per CLAUDE.md.

What the twins scan: every PHP log record and trace payload the controllers
emit, plus the sidecar lines returned by the endpoint for that request. The
real `retrieve.py` and critic code does not run in the twins, so a PHI leak
added to sidecar retrieval logging stays uncovered in the minimum slice (a
SURVIVED row if a mutant targets it).

The throwaway patient is the one `phi.php` already creates (line 92: Eval
PhiLogs, 1980-05-05). The ask twin's question is "Does Eval PhiLogs, born
1980-05-05, need a statin?", and both "PhiLogs" and "1980-05-05" are in the
case's `phi` list. The brief twin seeds a chart that fires a known trigger
(an LDL result above the lipid threshold, reusing case 68's seeded-SOAP
pattern for the prior plan note) and asserts that `guideline_status` is not
`no_triggers`, so it cannot pass without reaching the sidecar.

**F2. Prompt lock.** `tests/evals/fixtures/prompts.lock.json` (under the
directory already mounted read-only into the sidecar, so its pytest can read
it) holds sha256 hashes of
the *rendered* text sent to a model, not of source code, so comment edits do
not trip it and no Python parser is needed in PHP:

- PHP side (an isolated PHPUnit test, `PromptLockTest`): render
  `Prompt::briefingSystem()`, `followUpSystem()`, `briefingUser()` and
  `followUpUser()` on a fixed fixture (a small `AssembledFacts`, a fixed
  question, a fixed `EvidenceSet`) and compare each hash with the lock.
- Sidecar side (a pytest, `test_prompt_lock.py`): hash every module-level
  string in `llm.py` sent to a model (`SYSTEM`, `LAB_TASK`, `RETRY_TASK`,
  `INTAKE_TASK`, `CRITIC_SYSTEM`) and compare with the same lock. The test
  also discovers every `*_TASK` / `*SYSTEM` name in `llm.py` and fails if one
  has no lock entry, so a new prompt cannot bypass the lock.

Both tests already run in the plain push (the isolated PHPUnit and pytest
stages). On a mismatch they fail with
`PROMPT CHANGED: <name>. Re-record replies for the cases that use it, re-run the live cases, then run tests/evals/prompt-lock.php --update.`
The lock has its own update command, separate from `--update-baseline`, so
refreshing the golden-case baseline never silently accepts a prompt change.

Honest limit: this is a pin, not an eval. It cannot tell a good prompt edit
from a bad one, and nothing forces the live re-run before `--update`; it
makes a prompt change a deliberate, visible step with the live re-run named
in the message. The matrix reports kills by the lock separately from kills
by the evals.

### Part 2: the matrix

`tests/evals/mutants/` holds one small unified-diff patch per mutant, a
frozen `list.json` (id, layer, file, function, one-line mutation, expected
killer), and `run.sh`.

**Where it runs.** Only in a stack created with
`openemr-cmd worktree add mutants -b --base HEAD --start` (CLAUDE.md: never
raw `git worktree add`; the worktree has its own containers and port offset).
`run.sh` refuses to run when the checkout is not a managed worktree. It
resolves the worktree's own `openemr` and `copilot-sidecar` containers by
their compose project label and passes them to `gate.sh` through a new
`GATE_CONTAINER` override (a small gate.sh change, also useful for any
worktree), so the other session's primary stack is never picked up.

**Per mutant:**
1. `git diff --quiet` or abort (clean tree). A `trap` on EXIT/INT/TERM runs
   `git checkout -- .` and restores the sidecar, so an interrupted run never
   leaves the worktree mutated.
2. `git apply --check`; a patch that no longer applies is STALE and fails the
   run.
3. `git apply`. If the patch touches `sidecar/`: `docker cp` the changed files
   nothing extra is needed: `gate.sh` (Part 0) sees the source hash differ and
   rebuilds the worktree's sidecar itself. `run.sh` then reads
   `source_sha256` from `/health` and aborts if it does not match the
   checkout. (Wait on `/health`, not `/ready`: `/ready` returns 503 without
   an OpenAI key.)
4. Run `tests/evals/gate.sh pre-push` with a 10-minute timeout.
5. Classify:
   - **KILLED** only when the output names a refusal: a failed pytest or
     PHPUnit test name, `PROMPT CHANGED`, or a rubric line `BELOW` /
     `REGRESSED` with case ids. Record the stage (pytest, case index,
     PHPUnit, prompt lock, golden rubric) and the rubric and cases.
   - **SURVIVED** when the gate prints `GATE: PASS`.
   - **ERROR** for anything else (timeout, harness produced no results,
     container missing, PHP parse error). ERROR fails the run and is never
     counted as a kill.
   Expected versus actual killer is recorded; a mismatch is flagged.
6. `git apply -R`. The next gate run rebuilds the sidecar back to the
   unmutated source through the same Part 0 check.

**Control runs.** An unmutated `gate.sh pre-push` must print `GATE: PASS`
before the first mutant and again after the last. If either control fails
the run aborts and no result is written; the closing control is also what
detects database residue left by a crashed case.

**Output.** `tests/evals/mutants/results.json` records the tested commit SHA,
the hashes of `baseline.json` and `prompts.lock.json`, the date, and per
mutant: verdict, stage, rubric, cases, expected killer, mismatch flag. A
generator writes the table into `EVAL_GATE.md`. Results are committed on the
`mutants` branch and cherry-picked to `pdf_reader` (results files and the
table only). They are stale, and must be re-run before a submission, when
any file under `src/`, `sidecar/` or `tests/evals/cases/` changed after the
recorded SHA.

**Honesty rules.** `list.json` is frozen before the first run. A mutant is
never deleted or rewritten because it survived: it stays, marked SURVIVED,
until a fix kills it. The table reports the first-run kill rate beside the
final one, and marks each mutant killed only by a case written after that
mutant was seen.

The matrix is not part of the pre-push hook (each mutant is a full gate run,
roughly 1-2 minutes). It runs on demand and before each submission.
Reproducing it needs Docker, `openemr-cmd` and the worktree setup from
CONTRIBUTING.md; the steps are `openemr-cmd worktree add mutants -b --base HEAD --start`,
then `tests/evals/mutants/run.sh` inside that worktree.

The `--self-test` keeps its synthetic verdict flip (it runs in the primary
checkout, where mutants are not allowed). Evidence that a real code change is
refused comes from the matrix.

## Reviewer Concerns

### R2-1 — consistency

**Problem**

> The matrix and the real plain push run different sidecar code. The Constraints say the sidecar's code is baked into its image, and gate.sh runs `docker exec $sidecar python -m pytest` (line 84) and the sidecar golden cases against whatever image is running. Nothing in the hook rebuilds the image or checks it against the working tree. run.sh step 3 `docker cp`s each patched Python file in and restarts the sidecar, which the real hook never does. A grader who edits anchor.py, retrieve.py, graph.py, schemas.py or llm.py and runs `git push` is tested against the old image and passes. So the Python kills (M3-M8, M11) and success criterion 4 ('any model-bound string in llm.py fails the plain push') describe a gate the grader does not run, which contradicts the definition of 'plain push' in the Problem Statement.

**Remedy**

> Choose one. (a) Make gate.sh fail closed when the running sidecar does not match the checkout, for example by exposing a hash of the copilot_sidecar source on /health and having gate.sh compare it with the working tree, or by rebuilding and restarting the sidecar inside the hook. (b) Label every Python-layer kill and criterion 4 as 'assuming a rebuilt sidecar' and add a SURVIVED-by-construction row for an edit that is pushed without a rebuild. With (a), have run.sh use the same mechanism the hook uses, not a copy only the matrix makes.

### R2-2 — feasibility

**Problem**

> Step 3 of run.sh waits for `/ready` after restarting the sidecar. app.py `_readiness()` counts `openai_key` as a required dependency and returns 503 whenever OPENAI_API_KEY is unset (lines 164-179). A plain push is defined as running with no API key, so in that environment /ready never returns 200. Every Python mutant, and the trap's restore, would time out and be recorded as ERROR.

**Remedy**

> Wait on /health, or on a /ready body where every dependency except openai_key is 'ok'. Add a test that the wait succeeds on a stack with no key.

### R2-3 — feasibility
