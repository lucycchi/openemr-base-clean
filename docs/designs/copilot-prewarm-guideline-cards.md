## Problem Statement

The 06:00 pre-warm (`copilot:prewarm`) generates each scheduled patient's briefing so the physician's first chart open is a cache hit. It is built and switched off on the droplet. Since the Week 2 guideline cards were added, it is broken in five ways:

1. **Wrong narration key.** Commit `682492d` put the guideline chunk ids into `NarrationPipeline::cacheKey()`. Chart open builds the cards (`ChatController::guidelineSection()`), then narrates with their passages. The sweep narrates with no passages (`PipelineNarrator::brief()` → `NarrationPipeline::brief($assembled)`). For any chart with a surviving card, the two keys differ and the pre-warmed narration is never read.
2. **Cards not pre-built.** The sweep never builds the guideline section, so chart open still calls the sidecar (retrieval plus one critic call per card) even when the narration would hit.
3. **False hits.** `WarmOutcome::evaluate()` compares facts hash, prompt version and model only, so the misses in 1 are scored `warm_hit = true`.
4. **Wrong stored key.** `DbPrewarmReceipts::record()` recomputes `cache_key` with an old copy of the formula (no chunk-id suffix), so the stored key never matches any real cache row, for any patient. Nothing reads it today.
5. **Failures counted as warms** (found by the second opinion; a Week 1 bug). `Prewarmer::warm()` labels every non-cached result `warmed`, but `NarrationPipeline::brief()` returns an ordinary result with `cacheKey = null` when the model fails or the verifier strips everything. Nothing was stored, yet the receipt says "warmed" and the hit check says "hit".

The root cause of 1 to 4 is drift: the guideline step was added to the chart-open controller instead of the wiring the sweep shares (`BriefingPipelineFactory` exists precisely "so the panel and the sweep cannot drift apart").

No user is affected: the sweep is off (`COPILOT_PREWARM_ENABLED` unset, no cron line). It blocks turning the sweep on.

## What Makes This Cool

The pre-warm's promise was "every miss has a reason". Today it would report hits that never happened. After this, a hit means one thing, checked directly: the summary was served from the cache under exactly the key the 06:00 job wrote. And on a normal day (card status `built`), the physician gets the guideline cards at 09:00 with no sidecar call at all, because they were built and saved at 06:00. A `partial` run is never saved, so its cards are rebuilt at chart open by design; whether the cards came from the cache is logged separately from the summary hit.

## Premises (agreed)

1. The 06:00 job does exactly what chart open does: build the guideline cards (calling the sidecar), then narrate with those cards' passages, through one shared component, so the two paths cannot drift again.
2. A pre-warm hit is decided by comparing the exact key the job wrote with the exact key chart open reads, and requiring that the narration was actually served from the cache. The receipt stores the key the pipeline actually used, never a recomputation.
3. If the sidecar is down at 06:00, the job still caches a narration without cards. If chart open later builds cards, that is a miss with its own named reason and the chart regenerates, exactly as it does today without a pre-warm. Nothing watches the sidecar: every chart open with no saved cards calls it again, and failures are never cached. The receipt records the card status per patient: `built`, `partial`, `unavailable` or `none_fired`.
4. The job stays switched off.

Revision made during the session: **when the critic cannot assess a card, the card is still shown with its "applicability not assessed" label, but its passage is not offered to the AI summary.** The summary only restates guidance the critic vetted for this patient. This applies to both paths. (Today an unassessed passage can be restated in the summary with no warning on the sentence.)

This revision is a chart-open behavior change, independent of the pre-warm. It is made before the final because it is a safety fix the user chose as a clinician: prose should not restate a guideline that was not checked against this patient. It lands as its own commit with its own gate run, after the behavior-preserving extraction and before the pre-warm work, so each change can be judged and reverted alone. The same rule covers the case where the critic never ran (the sidecar has no model key, as in the keyless eval runs): the cards show as not assessed and the summary gets no passages. Production always has the key, since both containers read the same `.env`.

## Recommended Approach (A), in detail

**1. `Guidelines/GuidelineEvidence` (new).** The body of `ChatController::guidelineSection()`, moved, with these changes:
- Signature: `build(AssembledFacts $assembled, PatientId $pid, DateTimeImmutable $day, string $correlationId): GuidelineOutcome`. The day replaces `ServiceContainer::getClock()->now()`: chart open passes now, the sweep passes its pinned start of day. The correlation id is passed to `SidecarClient::brief()` as today; the sweep passes the same per-patient id it records on the receipt, so the sidecar's log lines join to the receipt.
- `GuidelineOutcome` carries: the `GuidelineSection`; the sidecar handoffs and usage (chart open copies them into its request state exactly as today; the sweep sums the usage, see point 3); `cardsFromCache` (bool); and a status for the receipt, one value for every path the code can take:

  | Status | When |
  |---|---|
  | `none_fired` | no trigger rule fired |
  | `built` | a complete, cacheable section: fresh from the sidecar, or served from the guideline cache (`cardsFromCache = true`), including every card rejected by the critic |
  | `partial` | a worker failed, or a card has no verdict (the critic failed or did not run): shown, not cached |
  | `unavailable` | the sidecar call failed, including a sidecar that is not configured on the site (the call fails before it is sent, and the code cannot tell the two apart) |

  An unreadable guideline cache entry is logged and rebuilt, as today; the status is whatever the rebuild yields.
- `GuidelineTriggers::cacheKey()` also hashes the active problem titles the critic receives, and whether the critic ran. A section built on a stack without a model key is therefore never served once the key is added: the next open builds it again with the critic.
- `vettedChunks()`: passages from cards whose verdict is `applicable === true` only (the session revision above). When the critic did not run, no card has a verdict, so the summary gets no passages.

Dependencies are constructor-injected (`ChartSource` for demographics, `SidecarClient`, `Config`, a cache factory per patient, `LoggerInterface`), so it is unit-tested with fakes. Chart open builds it with the `SidecarClient` the controller already accepts in its constructor (the hook `tests/evals/phi.php` uses to replay recorded sidecar replies).

**2. Chart open (`ChatController::brief()`).** Calls `GuidelineEvidence` instead of the private method, and passes `vettedChunks()` (not every card's chunks) to `NarrationPipeline::brief()`. The warm evaluation moves to after narration (point 5).

**3. The sweep.** `Prewarmer` receives `GuidelineEvidence` (behind a small interface so its tests keep using fakes) and, per patient: assemble as the scheduled provider with the pinned clock (unchanged), build the guideline evidence with the same pinned day, then narrate with `vettedChunks()`. `BriefingNarrator::brief()` gains the `EvidenceSet` argument. Status mapping in `Prewarmer::warm()`: `fromCache` → `already_cached`; stored (`cacheKey !== null`) → `warmed`; otherwise → `error` with the result's status label (`model failed`, `all sentences stripped`). `Bootstrap` wires it.

Sidecar cost at 06:00 is recorded: each patient's priced sidecar usage (retrieval, rerank, critic) is held on its in-memory `PrewarmRow`, `PrewarmSummary` totals it, and the `copilot.prewarm` trace carries the run's total as `sidecar_cost_usd` beside the existing `model_calls`. No receipt column: the per-patient figure is in the sidecar's log lines. The sidecar's own log lines carry the per-patient correlation id and per-call tokens.

**4. Narration key.** `NarrationPipeline::cacheKey()` appends `GuidelineTriggers::indexVersion()` when the evidence set is non-empty, so an edited corpus invalidates narrations that restated it. Facts-only keys are unchanged.

**5. Receipts and the hit check.**
- **Write side.** `PrewarmRow` carries the narration's actual `cacheKey` and the guideline status. `DbPrewarmReceipts::record()` stores them and stops recomputing the key.
- **Schema.** `guideline_status VARCHAR(16) NULL` added to `copilot_prewarm` in `install.sql`; upgrade script `0_1_4-to-0_1_5_upgrade.sql` with the `ALTER TABLE` and `UPDATE copilot_prewarm SET cache_key = NULL` inside one `#IfMissingColumn copilot_prewarm guideline_status` … `#EndIf` block, so the keys are nulled exactly once, when the column is first added, and a second Upgrade or a by-hand run changes nothing; `version.php` bumped to 0.1.5 with its comment line.
- **Read side.** `DbPrewarmReceipts::latestFor()` selects `guideline_status` and picks one row for the day in this order: the latest `warmed` or `already_cached` row (the opener's own first, as today); only if there is none, the latest `error` row, so a failed warm is visible at chart open. `skipped` rows (`--dry-run`) are never selected. A successful 06:00 warm is therefore not hidden by a later dry run or a failed manual rerun. `PrewarmReceipt` gains `guidelineStatus` and `status`; a NULL `guideline_status` (legacy row) reads as `unknown`.
- **The hit check.** `WarmOutcome::evaluate()` runs after narration, with the key this open read (`NarrationPipeline::cacheKey($assembled, $evidence)`, pure, so it is available even when the model failed at chart open) and `fromCache`. Order:
  1. `no_row`: no receipt today.
  2. `warm_failed`: the latest receipt has status `error` (the 06:00 narration failed).
  3. `prompt_version`, then `model_changed`: as today.
  4. **hit**: the receipt key is non-null, equals the key read, and the narration came from the cache.
  5. If the facts hash is equal: `receipt_key_unknown` (a legacy row whose key was nulled by the upgrade), `guideline_cards_differ` (keys differ; reported with the receipt's guideline status, so "unavailable at 06:00" is distinguishable from "the critic changed its mind"), or `cache_entry_missing` (keys equal, not served from the cache).
  6. Otherwise `viewer_differs` / `hash_drift`, as today.
- **A hit covers the summary only.** Whether the cards came from the cache is a separate log and trace field, `warm_cards_cached`. New `WarmMissReason` cases; new log keys (`warm_guideline_status`, `warm_cards_cached`) added to `LogFields::ALLOWED`; the miss-reason list in ALERTS.md section 6 updated.

Where the build departs from the text above, and why:

- **R2-5, "whether the critic ran" in the guideline key.** Not implementable: whether the critic ran is known only from the sidecar's reply, and the key is needed before the call to look up the cache. Implemented instead with the reviewer's other remedy: a section with any unassessed card (the critic failed or did not run) is not cached and is recorded as `partial`, so the next open builds it again. This reverses an earlier deliberate rule, "no critic configured: the section is complete", and costs one sidecar call per chart open on a stack without a model key.
- **The upgrade script.** `docker/vps/deploy.sh` strips every `#If` line and applies every upgrade file on every deploy, so the `#IfMissingColumn` guard alone would have re-run the `UPDATE` (wiping valid keys) and failed the `ADD COLUMN` on the second deploy. Each statement is now idempotent on its own: `ADD COLUMN IF NOT EXISTS` (MariaDB, which every stack here uses), and the `UPDATE` clears only keys with no guideline status, which only pre-0.1.5 receipts can have.
- **Kill matrix.** The mutant was run by hand, not added to `tests/evals/mutants/`; the matrix needs a worktree stack to re-run.

### R2-1 — clarity

**Problem**

> The receipt status table lists `not_configured` for 'the section cannot be built on this site (GuidelineSection status not_configured)', and Success Criteria commits to a `not_configured` test. But the code being moved (ChatController::guidelineSection()) has no branch that produces GuidelineSection::none('not_configured'). It returns only 'no_triggers', 'unavailable', or a section from fromRun() with status 'ok'. A sidecar that is not configured reaches SidecarClient::run(), which throws SidecarException('unavailable'), so today it would be recorded as `unavailable`, not `not_configured`. Premise 3 also lists only four receipt statuses and leaves out `not_configured`. So what the receipt records for an unconfigured sidecar is still undefined.

**Remedy**

> Either state the check GuidelineEvidence adds (for example, an empty Config sidecar URL returns GuidelineSection::none('not_configured') before any call) and test that condition, or drop `not_configured` and say that an unconfigured sidecar is recorded as `unavailable`. Make Premise 3's status list match the table.

### R2-2 — completeness

**Problem**

> Point 5 changes DbPrewarmReceipts::latestFor() to return the latest row for the day 'of any status'. Prewarmer::run() writes a PrewarmStatus::Skipped receipt for every patient on `--dry-run`, and Skipped is also used for rows that were not attempted. The hit-check order handles only `error`. If someone runs `--dry-run` after the real 06:00 warm, the Skipped row (null facts_hash, null cache_key) becomes the latest receipt and hides the real one. Chart open then reports viewer_differs or hash_drift against an empty fact list instead of a hit.

**Remedy**

> Leave `skipped` rows out of latestFor() (or add a named miss reason for them), and add a test: a real warm, then `--dry-run`, then chart open still reports a hit.

### R2-3 — consistency

**Problem**

> Because latestFor() takes the latest row of any status and `warm_failed` is checked before the hit, a later `error` row hides an earlier successful receipt for the same day. For example, 06:00 stores the narration (`warmed`), then a `--force` rerun at 07:00 fails for that patient (`error`). Chart open is served from the cache under exactly the key the 06:00 job wrote, yet it is reported as `warm_failed`. This contradicts 'a hit means ... the summary was served from the cache under exactly the key the 06:00 job wrote'.

**Remedy**

> Define the row-selection rule. For example, prefer the latest `warmed` or `already_cached` row (the opener's own first), and fall back to an `error` row only when no successful row exists that day. Add the warmed-then-error rerun to the tests.

### R2-4 — clarity

**Problem**

> Point 3 says 'the sweep adds each patient's priced sidecar usage ... to its row'. It does not say which row. If it means the copilot_prewarm receipt, that needs a column, but the schema change adds only `guideline_status`. If it means the in-memory PrewarmRow or PrewarmSummary, the per-patient cost is lost after the run except in sidecar logs. The Next Steps list says only 'sidecar cost on the sweep trace'.

**Remedy**

> Say where per-patient sidecar cost is stored: a new receipt column (added to install.sql, the guarded upgrade and the tests), or PrewarmRow/PrewarmSummary only, with just the run total on the `copilot.prewarm` trace.

### R2-5 — completeness

**Problem**

> A section built when the critic did not run (sidecar with no model key) is `built`, cacheable, and all its cards have applicable === null. The guideline cache key (facts hash, fired triggers, age, sex, model, index version, and now problem titles) does not show whether the critic ran. If such a section is cached, for example on a dev or demo stack that once ran without the key, it keeps being served after the key is added. Its cards stay 'not assessed' and, under the new vetted-only rule, the summary gets no guideline passages until the facts change. The claim 'production always has the key' covers the droplet but not stacks that already hold keyless cache rows.

**Remedy**

> Either make a section with no critic verdicts non-cacheable, or add whether the critic ran to the guideline cache key. Otherwise state that stacks that ran without the key must clear their guideline cache rows before the demo, and add that to the deploy notes.
