## Problem statement

The graders asked for an `EVAL_GATE.md` at the repo root, due before tonight's
Early Submission. It has to cover five things:

1. where the prompts, schemas and golden set live;
2. how to install and trigger the gate;
3. what the gate runs, its rubrics and its thresholds;
4. which API keys or environment variables it needs;
5. proof that the gate blocked a regression.

They will mostly review the gate by reading the repo, but may run it on some
submissions, so it has to work from a fresh clone.

## What was settled in this session

- **The gate stays the client-side pre-push hook.** GitLab will not run
  pipelines for this project: `POST /projects/1993/pipeline` returns 403 even
  though the user is Owner with an `api` token. The project has had 0 pipelines
  despite a committed `.gitlab-ci.yml`, and there are no runners. The
  instructors confirmed a hook is enough: *"You don't need a CI runner to meet
  this... swap item 5 for proof of a blocked commit instead: a screenshot or
  short clip of your hook failing on a regression you introduced, linked in
  EVAL_GATE.md. Either way, include the install command."*
- **Ruled out:** our own GitLab runner on a resized droplet or a new droplet
  (GitLab refuses to create pipelines, so a runner would never get a job);
  asking the maintainers for runners (not needed after the instructors'
  answer); GitHub Actions (wrong repo for grading).
- **Item 5 is a committed screenshot plus the plain-text log** of `git push`
  being refused after a real, deliberate regression.
- **Everything is rehearsed from a brand-new clone** (approach B below), so the
  proof also shows the gate works from a clean checkout.
- **EVAL_GATE.md is a short index for graders.** It links to
  `tests/evals/README.md` and `contracts/` instead of copying them.
- **The GitLab default branch becomes `pdf_reader`.** Today it is `audit`,
  which is 59 commits behind and has none of the Week 2 gate files. A grader
  who opens or clones the repo would otherwise land on old code. The droplet
  deploys by hand and does not follow the default branch, so this does not
  affect the demo.
- **Small fix to `install-hooks.sh`:** find the hooks folder with
  `git rev-parse --git-path hooks` instead of assuming `$root/.git/hooks`.
  The old assumption breaks in git worktrees, where `.git` is a file.

## Approaches considered

- **A. Doc first, fresh-clone test afterwards** (~45 min). Faster, but the
  proof would come from the everyday setup, and anything the clean clone turns
  up would force the doc to be redone.
- **B. Everything from a fresh clone. Chosen** (~1.5 h). One run proves both
  that the hook blocks a regression and that it works from a clean checkout.
- **C. B plus a one-command setup script** (~2 h). More polished for graders,
  but it is extra code on a deadline night and the instructors only asked for
  the install command.

## Recommended approach (B), step by step

1. **Pause the everyday stack** (`docker compose stop` in
   `docker/development-easy`). This keeps its data; it starts again at the end.
2. **Clone into a scratch folder** from GitLab (`pdf_reader`), exactly as a
   grader would. With no `.env`, there are no API keys, which matches a grader.
3. **Start the clone's stack under its own compose project name**
   (`docker compose -p gatefresh up -d --wait`). This matters: compose names
   volumes after the project, and the default name comes from the folder
   (`development-easy`). Without `-p`, the clone would reuse the everyday
   database volume, so it would not be a fresh database and could damage the
   everyday one. A grader with a single clone doesn't need `-p`.
4. **Install the hook and run the self-test:**
   `tests/evals/install-hooks.sh --self-test`.
5. **Confirm a clean push passes:** `tests/evals/gate.sh pre-push` should print
   `GATE: PASS`. If the database-backed `facts` cases fail on the fresh
   database (see open question 1), fix that before going further.
6. **Inject the regression:** in `src/Verifier.php:42`, stop the verifier
   removing sentences that carry no citation (the `factIds === []`
   condition). Commit it on a branch named `gate-proof`, then
   `git push gitlab gate-proof`. Expected output: the failing cases and
   rubrics, `GATE: FAIL (push refused)`, and
   `failed to push some refs to ... labs.gauntletai.com`. The push is refused
   before anything leaves the machine.
7. **Capture the proof.** Record the terminal session with `script`, commit the
   raw log, and commit a screenshot of the same output under
   `clinical_copilot_week2/eval-gate-proof/`.
8. **Revert the regression and push again.** The push should pass. The
   `gate-proof` branch then exists on GitLab with the regression commit and
   its revert, which a grader can inspect.
9. **Write EVAL_GATE.md** from what actually happened, including any extra
   steps the clean clone needed. Commit it together with the proof files and
   the installer fix on `pdf_reader`, push, and switch the GitLab default
   branch.
10. **Tear down** the `gatefresh` stack (`docker compose -p gatefresh down -v`),
    then start the everyday stack again.

## EVAL_GATE.md outline

1. **Prompts, schemas and golden set.**
   - Prompts: the module's prompt classes (`Prompt::VERSION`) and the sidecar's
     prompts.
   - Schemas: `interface/modules/custom_modules/oe-module-clinical-copilot/contracts/*.schema.json`.
   - Golden set: 52 cases in `tests/evals/cases/`, fixtures in
     `tests/evals/fixtures/`, baselines in `tests/evals/baseline.json` and
     `tests/evals/baseline-live.json`.
   - All of these are committed.
2. **Install and trigger.**
   - Prerequisites: docker, and the dev stack started with
     `cd docker/development-easy && docker compose up -d --wait`.
   - Install: `tests/evals/install-hooks.sh --self-test`.
   - Trigger: `git push`, or run it directly with `tests/evals/gate.sh pre-push`.
   - The pre-commit entry in `.pre-commit-config.yaml` runs the same gate.
3. **What the gate runs and when it fails.**
   - It runs, in order: the sidecar's pytest, the case-index check, the
     module's isolated PHPUnit suite, then the golden cases through `gate.php`.
   - Thresholds are 100% for `schema_valid`, `citation_present`,
     `anchor_correct`, `no_phi_in_logs` and `applicability_correct`, and 90%
     for `factually_consistent`, `safe_refusal` and `routing_correct`.
   - It also fails if a rubric falls more than 5 points below the baseline.
4. **Keys and environment variables.**
   - None for the default (deterministic) run.
   - `OPENAI_API_KEY` (and optionally `COHERE_API_KEY`) in the root `.env`,
     with `COPILOT_GATE_LIVE=1`, adds the live cases.
5. **Proof.** A link to the screenshot and log, the `gate-proof` branch on
   GitLab, and one line explaining why there is no merge request (GitLab
   refuses student pipelines; the instructors said to substitute this proof).

## Open questions (to settle during the build)

1. **Do the `facts` cases pass on a fresh database?** `run.php:85-98` loads
   `globals.php` and connects to the database when a non-pending `facts` case
   exists. A fresh install has no demo patients and may not have the module's
   tables until the module is enabled. The rehearsal answers this. If they
   fail, either the cases create their own data, or EVAL_GATE.md documents the
   one setup step needed.
2. **Should `gate.sh` stop requiring `openemr-cmd`?** Graders are unlikely to
   have it installed (it comes from openemr-devops). `gate.sh` uses it only for
   `openemr-cmd e`, which is a `docker exec` into the openemr container. The
   proposal is to call `docker exec` on the container `gate.sh` already
   detects, removing the dependency. That is a small change, and it also
   avoids `openemr-cmd` picking the wrong stack when two are running.
3. **How is the screenshot made?** Options: the user takes it of the real
   terminal, or it is rendered from the captured log. Either way the raw log
   is committed next to it.

## Success criteria

- `EVAL_GATE.md` is at the root of `pdf_reader`, which is GitLab's default
  branch, and covers all five items.
- The steps in it were run, as written, from a fresh clone with a fresh
  database and no API keys, and ended in `GATE: PASS`.
- The committed screenshot and log show a real `git push` to GitLab refused
  by the hook, and the `gate-proof` branch shows the regression and its revert.
- The everyday stack is running again with its data intact.

## Dependencies

- Docker on the host; the development-easy stack must boot from scratch (the
  first boot runs composer and npm, which takes several minutes).
- SSH push access to `labs.gauntletai.com` (already works on this machine).
- The GitLab token in `.env` (`api` scope) to change the default branch.
