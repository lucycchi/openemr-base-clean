### Part 1: Lab trend chart (target 02:15 to 04:15 CT)

1. **Series in PHP.** A small readonly value object `LabSeries` holds the LOINC,
   the name, the unit, and the points as a list of `{date, value, citation|null}`.
   `FactAssembler` builds the series from the `$labs` list it already filtered
   and sorted (`FactAssembler.php:185-188`). The rules:
   - Numeric values only (`LabRecord::isNumeric()`).
   - A row with an empty LOINC is excluded. Grouping on an empty code would
     merge unrelated tests that share a unit, which is the same reason the delta
     logic skips them.
   - A row dated at the 1970-01-01 sentinel (a missing or zero date in
     `OpenEmrChartSource`) is excluded.
   - A row with `unitMismatch = true` is excluded. Its printed unit is not the
     one the LOINC map expects, so it cannot sit on the same axis. It still
     surfaces as a fact.
   - Grouping key: LOINC plus the unit trimmed and case-folded. A real unit
     change starts a separate series, never a mixed line.
   - Points run oldest first, and a series needs at least 2 points after the
     exclusions above.
   - Two points on the same date are kept only if their values differ. If a
     chart value and a document value on the same date are equal, the cited one
     is kept, because it is the same draw recorded twice.
   - Cap: at most **6 series**, ordered by most recent result first, and at most
     the **8 latest points** per series. Anything over the cap is counted, and
     the panel shows "N more tests with trends not shown", the same pattern the
     facts use.

   `AssembledFacts` carries the series the way it carries `latestBmi`, and it is
   never a fact, so the facts hash and the briefing cache key do not change.
2. **Payload and contracts.** `PanelPayload::base` adds `trends`
   (`{series: [{loinc, name, unit, points: [{date, value, citation}]}], more: int}`),
   where `citation` is the existing `Citation::toArray()` or null for a
   chart-entered value. Because `base()` feeds the briefing, answer and
   chart-changed responses, all three schemas
   (`chat.briefing`, `chat.answer`, `chat.chart-changed` `.response.schema.json`)
   gain the `trends` property, referencing `citation.schema.json`, and
   `ContractsTest` fixtures are updated.
3. **Panel.** `panel.js` gains `renderTrends(payload.trends)`:
   - One inline SVG per series, about 240x60. Nodes are created with
     `document.createElementNS` and every label is set through `textContent`.
     There is no `innerHTML`, because analyte names can come from uploaded PDFs.
   - The x position is proportional to the date, so irregular intervals are not
     drawn as even steps. The first and last dates are labelled.
   - The y range is the min to max of the series, padded by 10 % of the range,
     with a floor of 10 % of the latest absolute value. A flat series (all
     values equal, a range of 0) is drawn as a centred horizontal line, never a
     division by zero.
   - The latest value and unit are shown as text.
   - A chart value is a solid dot. A value read from a document is an outlined
     dot, and clicking it calls
     `window.copilotSourceViewer.open(docUrl(c.source_id), c, ...)` exactly as
     `openSource()` does for fact links (`panel.js:264`).
   - Unanchored document values do not reach `LabRecord`, because
     `copilot_document_fact.procedure_result_id` is set only for anchored rows.
     Unverified extracted values are therefore not charted; they keep surfacing
     as `extraction_unverified` facts. Confirm this join in step 1. If it does
     not hold, pass the citation unchanged and add a hollow style.
   - Each series gets a visually hidden table built with the existing `el()`
     helper, so screen readers get the values.
   - The section is hidden when `trends.series` is empty.
4. **Tests.**
   - An isolated PHPUnit test for the series builder: ordering, the 2-point
     minimum, non-numeric values dropped, empty LOINC dropped, the sentinel date
     dropped, `unitMismatch` dropped, the unit-key normalisation, same-day
     de-duplication, the caps with the `more` count, and the citation carried.
   - **Gate runner extension:** the `facts` mode in `tests/evals/run.php` gains
     an optional `expect.trends` key that compares the series LOINCs, the point
     counts, and which points carry a citation. This is committed scope (about
     20 min), so X4 has a real gate case.
   - Gate case 74: a chart with two LDL results in `mg/dL` plus one extracted
     LDL in `mg/dl` gives one 3-point series whose last point carries the
     document citation.
5. Commit: `feat(copilot): lab trend chart in the panel`.

### Part 2: Medication list document type (target 04:15 to 06:30 CT)

1. **Contracts** (module `contracts/`):
   - `documents[].doc_type` in the run request schema, and
     `documents.request.schema.json`, add `medication_list`.
   - A new `medication-list.schema.json` for the output and a new
     `llm.medication-list-proposal.output.schema.json` for the model proposal.
   - `test_contracts.py` and `ContractsTest` cover both new shapes.
2. **Sidecar** (`sidecar/copilot_sidecar/`):
   - `schemas.py`: `DocType` adds `"medication_list"`. There is a new
     `MedicationListProposal` (`patient_name`, `list_date`, and `medications` as
     a list of the existing `IntakeMedicationProposal`) and a new output
     `MedicationList` (`doc_type = "medication_list"`, `patient_name_on_list`,
     `list_date`, `list_date_citation`, and `medications` as a list of
     `IntakeMedication`). `Extraction` accepts the third shape.
   - **Field mapping:** the printed drug column becomes `name`, strength becomes
     `dose`, and directions become `frequency`. The "last filled" column is not
     extracted.
   - `llm.py:255-256`: the if/else becomes a lookup table by `doc_type`. The new
     `MED_LIST_TASK` prompt extracts only what is printed and copies the strength
     and directions verbatim, because the anchor matches digit-bearing details
     exactly.
   - `anchor.py`: `build_medication_list` reuses the per-entry anchoring helper
     and the date anchoring that `build_intake_form` uses.
   - `extractor.py:90-95`: dispatch the third type. `graph.py:58`: add it to
     `SUPPORTED_DOC_TYPES`.
3. **PHP** (module `src/`):
   - `DocType::MedicationList = 'medication_list'`, with `categoryName()`
     returning `'Medical Record'`.
   - `SidecarClient` validates a `medication_list` extraction against
     `medication-list.schema.json`.
   - `ExtractionResult::fromArray` (line 67) dispatches `medication_list` to
     `IntakeExtraction`, and `IntakeExtraction::fromArray` (line 49) branches on
     `doc_type`. For `medication_list`, demographics are absent, the allergy and
     family-history lists are optional and empty, and `list_date` with its
     citation becomes the `form_date` item, stored at `field_path` `/list_date`.
   - **Wrong-patient check:** `DocumentIngestService` routes the list to
     `persistIntake`, which compares `patient_name_on_list` with the chart
     through the existing `demographicsMismatches($pid, ['name' => ...])`. On a
     mismatch it inserts the same fixed-sentence `patient_mismatch` row the lab
     path writes (`DocumentIngestService.php:205-209`), at `field_path`
     `/patient_name_on_list`. The printed name is compared and thrown away,
     never stored.
   - **Wording:** `OpenEmrChartSource::intakeRecords` selects `cd.doc_type`, and
     `IntakeRecord` carries it. `IntakeRecord::describe()` words
     medication-list rows as "Outside medication list (date) shows X dose
     directions" instead of "Patient lists X on the intake form". Otherwise
     pharmacy-dispensed data would be misattributed as patient-reported. Gate
     case 76 (below) asserts the wording.
   - The upload dropdown (`Bootstrap.php:163`), the `DocumentRequest` error text
     (line 82) and the `AttachCommand` usage text name the new type.
4. **Schema:**
   - `install.sql` gets `ENUM('lab_pdf','intake_form','medication_list') NOT NULL`.
   - A new `sql/0_1_5-to-0_1_6_upgrade.sql` holds
     `ALTER TABLE copilot_document MODIFY doc_type ENUM('lab_pdf','intake_form','medication_list') NOT NULL;`
     with the full definition, `NOT NULL` included. Running it again does
     nothing, which fits deploy.sh re-running every upgrade statement.
   - `version.php` bumps `$v_patch` to `'6'`.
5. **Fixture and cases:**
   - `tools/generate_fixtures.py` adds `medication-list.pdf`: a synthetic
     pharmacy printout with the patient name, a list date, and a table of drug,
     strength, directions and last filled. Each medication's strength and
     directions sit on one printed row. There is also a recorded `model.json`.
   - `anchor` gate case 75: every medication is anchored to its own row, and a
     swapped strength comes back `anchored: false`.
   - `facts` gate case 76: medication-list items become cited facts with the
     medication-list wording.
   - A pytest covers `build_medication_list`, and a PHPUnit test covers the
     wrong-patient row.
6. Commit: `feat(copilot): medication list document type`.

### R2-1 — feasibility

**Problem**

> Part 2 step 1 adds medication_list to run.request and documents.request and adds medication-list.schema.json, but never adds it to run.response.schema.json, whose extractions[].extraction is oneOf [null, lab-report.schema.json, intake-form.schema.json]. Per contracts/README.md, SidecarClient validates every sidecar reply against run.response before parsing, and intake-form.schema.json pins doc_type to 'intake_form'. So every medication-list reply would match no branch and be refused as schema_mismatch before the new per-type validation in step 3 runs. This is the part of R1-1 ('any response/extraction schema that enumerates it') that is still not done.

**Remedy**

> In Part 2 step 1, add {"$ref": "medication-list.schema.json"} to the extraction oneOf in run.response.schema.json. Add an accept example and a reject example for run.response with a medication-list extraction, so ContractsTest and test_contracts.py both exercise it.

### R2-2 — completeness

**Problem**

> documents.list.response.schema.json and documents.upload.response.schema.json both enumerate doc_type as ['lab_pdf','intake_form'], and the design does not update either. After a medication list is uploaded, the upload reply and every later list reply for that patient would break their contracts. The eval harness checks the list response for schema validity (PHI cases 36-38, rubric schema_valid), so the committed gate could go red on any patient with a medication list.

**Remedy**

> Add medication_list to the doc_type enum in documents.list.response and documents.upload.response (and in any other documents.* schema that lists it). Update their examples files, and add both to the Part 2 contract step.

### R2-3 — consistency

**Problem**

> The wrong-patient row for a medication list reuses the lab path's fixed value 'patient name on the report does not match the chart'. OpenEmrChartSource::intakeRecords reads it back through its patient_mismatch UNION branch, and IntakeRecord::describe() words every patient_mismatch as 'Lab report uploaded <date>: ...'. The warning would call a pharmacy medication list a lab report. The design changes the wording only for medication rows, not for this mismatch row, and the success criterion 'A list with another patient's name raises patient_mismatch' says nothing about how it reads.

**Remedy**

> Say that the patient_mismatch branch of intakeRecords also selects cd.doc_type. Give describe() a medication-list wording for patient_mismatch (for example 'Outside medication list uploaded <date>: patient name on the list does not match the chart'), or store a list-specific fixed value. Assert that wording in the PHPUnit wrong-patient test.

### R2-4 — feasibility

**Problem**

> The design does not say how patient_name_on_list and the document type get from IntakeExtraction to persistIntake. Today IntakeExtraction holds only items and demographics, and persistIntake writes every demographics mismatch as a demographics_mismatch row in copilot_intake. If the name goes into demographics['name'], the existing loop writes a demographics_mismatch row ('Intake form uploaded ...') instead of the promised patient_mismatch row in copilot_document_fact. If the name is dropped, no check runs at all. The medication-list contract also does not say whether patient_name_on_list may be null, as patient_name_on_report may be.

**Remedy**

> Decide where the name and type live: for example, IntakeExtraction gains a DocType and a nullable patientNameOnList (the demographics array stays empty for lists), and persistIntake branches on the type. Say that patient_name_on_list is string-or-null in medication-list.schema.json, and that a null name skips the check, as it does for lab reports.

### R2-5 — consistency

**Problem**

> Several places the user can see still call medication-list data 'intake form'. The rows use FactCategory::IntakeMedication, whose panel.js heading is 'Medications listed on the intake form' and whose truncation label is 'intake medications'. The facts are built with service 'IntakeForm', which shows in the chip tooltip. renderDocuments labels any doc_type that is not 'lab_pdf' as 'intake form'. So a row worded 'Outside medication list ... shows X' would sit under an intake-form heading, and the uploaded file would be listed as an intake form. This undoes the misattribution fix the design commits to.

**Remedy**

> Choose one: add a separate FactCategory (for example medication_list_med) with its own heading, truncation label, fact.schema.json enum value and FactCategory::cases() check; or rename the shared heading to something neutral such as 'Medications from uploaded documents'. Also give renderDocuments a 'medication list' label, and decide what fact source name medication-list rows carry.

### R2-6 — clarity

**Problem**

> The medication-list wording 'Outside medication list (date) shows X dose directions' does not say which date it shows. Showing the upload date would make a months-old dispensing list look current. Showing the list date means the query has to fetch it.

**Remedy**

> State which date appears in the wording. If it is the printed list date, say how describe() gets it (for example, intakeRecords joins the document's form_date row) and what is shown when the list has no date.
