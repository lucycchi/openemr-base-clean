## Problem Statement

A primary care physician with a 20-patient day has ~90 seconds between rooms
to recall who they're seeing, what changed since last visit, and what needs
attention today. Right now that means manually scanning notes, labs, and
meds under time pressure. The PRD (AgentForge Clinical Co-Pilot, Gauntlet AI
Week 1) requires a multi-turn conversational agent embedded in OpenEMR to
solve this — explicitly not a dashboard, search bar, or report generator.

## What Makes This Cool

The agent's opening message does the "what changed since last visit"
diffing work a physician currently does in their head, every single time,
across every chart tab — and every claim it makes is checked at the
database-field level before it's shown, so it's not just fast, it's
provably not making things up. The "whoa" moment is a physician asking a
follow-up mid-briefing and getting a cited answer instead of clicking
through three more tabs.

## Constraints

- Core interface is fixed by the PRD: multi-turn chatbot, tool-calling, not
  a dashboard.
- Agent surface area must trace to a validated PCP use case (to be
  formalized in [`USERS.md`](../USERS.md), which this design doc's premises feed — not yet
  written) — no speculative tool-chaining.
- Every claim must be source-attributed; domain constraints (interaction
  flags) must be enforced.
- Wednesday 2026-09-16 (Early Submission) hard-gates a deployed, working
  agent. This design scopes to that deadline first.
- Repo audit ([`AUDIT.md`](../AUDIT.md)) already found: auth is often menu-gated, not
  ACL-gated (UI hides a link but doesn't block direct access); no caching
  layer; no cron/job queue by default; N+1 patterns in shared services; no
  "encounter-finalized" event; audit log has unencrypted PHI and a checksum
  that's computed but never verified; 99.8% of seeded encounters reference
  a non-existent facility ID.

## Premises

1. Core interface: multi-turn chatbot (PRD-mandated).
2. Target user: PCP with a 20-patient day (not hospitalist/ED resident).
3. First workflow: chat opens automatically with "what changed since last
   visit + flags," then supports physician follow-up questions.
4. **[Revised after cross-model review]** MVP tool count: narrow (2-3
   tools — recent encounters/changes, active meds, allergy flag).
   **Drug-interaction flagging is explicitly out of v1 scope.** There is
   no source of truth for interactions in this OpenEMR install (no
   interaction rule table or external drug-knowledge service is wired up),
   and letting the LLM decide "drug A + drug B = interaction" from general
   knowledge is exactly the ungrounded clinical claim the PRD forbids. v1
   flags only what is *in the record*: documented allergies against active
   or newly prescribed medications. Adding a real interaction source (a
   rule table, or an external service such as RxNorm/NLM interaction APIs)
   is a future-iteration item and should be tracked as such. Works for any
   of the 30 seeded patients by default. The two risks the cross-model
   review raised against this (authz on the tool-call path, facility-ID
   nulling) were resolved by static inspection — see the Validation Spike
   section: the tool layer must do its own ACL checks, and the facility
   join is a `LEFT JOIN` so rows survive.
5. Verification: claims must be checked at **value level** — the specific
   claimed value (drug name, dose, date) must match the specific source
   field it's attributed to — not just **table level** ("came from the
   right service"). Driven by a live web-search finding: "entity-attribution
   failure" is a documented 2026 clinical-RAG failure mode where a system
   cites a real, correctly-formatted source but attributes the wrong
   entity's data to it, passing naive "has a citation" checks.
6. Differentiator vs. OpenEMR's existing chart/encounter tab views: the
   agent's value-add is cross-time synthesis/diffing plus enforced
   per-claim citation — not new data that isn't already visible somewhere
   in the UI.

## Verification Architecture: Facts First, Narrative Second

The LLM never generates clinical facts. This is the structural answer to
both the citation problem and the omission problem, and it reuses the
`ChartFacts` assembly idea from [`AI_INTEGRATION_PLAN.md`](../AI_INTEGRATION_PLAN.md).

1. **Deterministic fact assembly (PHP, no LLM).** For the patient, the tool
   layer builds a typed fact list where every entry already carries
   `{id, service, record_id, field, value, category}` — encounters since
   last visit, medication changes, allergies, abnormal labs, new problems.
   Categories are fixed; the set is complete for those categories by
   construction.
2. **LLM narrates by reference, not by restatement.** The model receives
   the fact list and writes the briefing using fact IDs (`[F12]`), never
   values. Rendering substitutes the real value from the fact table. A
   drug name or date that isn't in the table cannot appear in the output.
3. **Verifier rules (deterministic, post-LLM):**
   - A sentence with no fact reference is stripped and replaced with the
     `[unverified — removed]` marker. Uncited prose never reaches the
     physician.
   - A referenced ID that doesn't exist in the fact set strips the sentence.
   - Any number or date token the model emits must appear verbatim in a
     referenced fact's rendered value, or the sentence is stripped (revised
     in the eng review, D16: narration is ID-only; computed deltas such as
     "A1c up 0.8" are facts the assembler emits, so the model never does
     arithmetic and no value normalizer is needed).
4. **Omission guard (coverage check).** Must-surface categories for v1:
   new or changed medications, new or changed allergies, abnormal labs
   since last visit, new problems. After narration, a deterministic pass
   checks that every must-surface fact ID appears in the output. Missing
   ones are appended in a fixed "Also on file since last visit" section
   rendered directly from the fact table with no LLM involvement. The model
   controls ordering and prose for these categories, never presence.
   Rationale: the physician-feedback study surfaced during research found
   omissions reported roughly 9x more often than hallucinations; a
   briefing that verifies every claim it makes but skips the new allergy
   is still a failure.

Known limitation: the verifier can only guarantee fidelity to the fact set.
If fact assembly itself is wrong (bad join, the facility-ID data-quality
issue, a category not yet covered), the output is faithfully wrong. That is
why the validation spike (premise #4) targets fact assembly, not the LLM.

## Operational Specifics (added after adversarial review)

- **Verification-failure behavior:** a claim that fails the value-level
  check is stripped from the rendered response and replaced with a visible
  `[unverified — removed]` marker in its place — never silently dropped,
  never silently passed through. No retry loop for v1 (retrying against the
  same mismatched data wouldn't fix a real attribution failure); a failed
  claim is a signal to log and review, not to re-ask the LLM for.
- **"Since last visit" boundary:** given no `encounter-finalized` domain
  event exists (per audit), the diff tool uses the most recent *prior*
  encounter for the patient by date, regardless of that encounter's
  status — this is a stated assumption, not a validated one, and should be
  checked against real data during the validation spike (premise #4) since
  encounter status/completeness quality is unknown per the audit's
  data-quality findings. **No-prior-encounter case:** if the patient has no
  prior encounter on record, the briefing states "first visit on record —
  no comparison available" and skips the diff section entirely; safety
  flags (allergy-vs-medication) still run normally since they don't depend on
  a prior encounter existing.
- **All-claims-failed state:** if every claim in an opening briefing fails
  value-level verification (e.g., the spike-uncovered authz/facility-ID
  issue manifests at runtime for a specific patient), the briefing does not
  render a wall of `[unverified — removed]` markers — it shows a single
  distinct message ("Unable to verify chart data for this patient right
  now — showing raw chart view only") and falls back to linking the
  existing OpenEMR chart tabs, rather than presenting a degraded-looking
  chat response as if it were normal.
- **Chat panel failure isolation:** the auto-opening briefing is loaded
  asynchronously, independent of and non-blocking to the underlying
  chart/encounter page render. If the agent/LLM call errors, times out, or
  is slow, the chart page renders normally regardless and the chat panel
  shows its own loading/error state — a stuck or failing agent call must
  never block or delay access to the chart itself, since that would be
  strictly worse than not having the feature at all on a high-frequency
  clinical screen.
- **Latency budget:** target under 5 seconds from chart-open to rendered
  briefing (leaves ~85s of the 90s window for the physician to read/act).
  The verifier checks narration against the in-memory fact set assembled
  in the same request (eng review D12); it never re-fetches. The cost is
  fact assembly itself: the audit found no caching layer and N+1 patterns
  in the same shared services this tool sits on, so the 5s number is an
  untested assumption. **Fold a timing check into the validation spike script**
  (premise #4, Next Steps step 1) — time the actual tool-call round trip
  for the 5-10 spike patients alongside the authz/facility-ID checks,
  rather than treating latency as a separate unvalidated risk.
- **Auto-open trigger:** the briefing chat opens on page load of the
  patient's encounter/chart screen in OpenEMR — not a separate button click
  — since the "90 seconds between rooms" scenario requires zero-friction
  access.
- **Multi-turn state:** the browser holds the transcript and posts it with
  every turn along with `facts_hash`; the server recomputes facts, and if
  the hash differs it returns "chart changed" and the thread restarts (eng
  review D1, D8). No conversation table for v1; persistence is tracked in
  TODOS.md. Correlation IDs come from a Monolog processor, independent of
  conversation storage.
- **Testing strategy for Wednesday (eng review D21):** eval harness
  (recorded fixtures + `--live`), unit tests for `Verifier` and
  `OmissionGuard`, and a curl smoke script over 10 pids as admin and as a
  restricted user. The dashboard regression E2E, the remaining Panther
  flows, and DB-backed ACL/sensitivity/prior-encounter tests land in the
  Wed→Sun window. See the Engineering Review section for the full test
  diagram.
- **PHI/audit-log interaction:** this feature writes new PHI-touching
  traffic (tool calls, LLM requests/responses) into the correlation-ID
  logging the PRD requires. It does **not** attempt to fix the audit log's
  existing gaps (unencrypted PHI, unverified checksum) — noted here as an
  explicit non-goal, not a silent omission, since fixing that is a
  separate, larger audit-remediation item.

**Approach ruled out during this session:** [`AI_INTEGRATION_PLAN.md`](../AI_INTEGRATION_PLAN.md)'s
original design (nightly-refreshed prose chart/visit summaries with an
e-sign workflow) — written before the audit existed and before the PRD's
conversational-agent requirement was fully reasoned through. Its
`ChartFacts`-assembly pattern and typed-service reuse are still useful
inputs to the tool layer below; the e-sign/nightly-batch shape itself is
deferred, not part of this design.

## Approaches Considered

### Approach A: Minimal viable — direct service calls, no framework
PHP tool functions call `src/Services/*` directly, a small router maps LLM
tool-call requests to them, verification is a standalone PHP function. No
agent framework. Fewest moving parts, easiest to defend in interview;
tradeoff is more boilerplate per tool and hand-rolled multi-turn state.

### Approach B: Agent framework (LangGraph / native tool-use loop)
Use a lightweight framework or the LLM provider's native tool-use loop for
orchestration; verification stays a separate deterministic layer outside
it. Less hand-rolling, easier to grow tool count later; tradeoff is a new
dependency to debug under deadline pressure and risk the framework's
abstraction obscures where verification needs to intercept.

## Recommended Approach

**Approach C: Hybrid** — build Approach A's simplicity for Wednesday, but
define tool functions with clean typed input/output schemas (the PRD's own
"contracts as source of truth" requirement) so migrating orchestration to a
framework later, if Sunday's scope grows, is a swap of the router/loop, not
a rewrite of the tools or verifier. Chosen because it ships as fast as the
minimal option while not foreclosing the framework question, and the typed
contracts are required by the PRD regardless of which option was picked.

## Decisions Made (formerly blocking open questions)

- **LLM provider: OpenAI.** Tool contracts are OpenAI function-calling JSON
  Schema; the fact-ID narration step uses Structured Outputs (strict JSON
  schema) so the model can only emit fact references, not free values.
  The PRD says to assume a BAA with any provider, so compliance was not a
  differentiator.
- **Deployment: single VPS running the `openemr/openemr:flex` image with
  the fork bind-mounted** (a trimmed copy of `docker/development-easy`'s
  openemr + mariadb services; no selenium/phpmyadmin/couchdb/ldap/mailpit),
  TLS via the image's own 443 or Caddy. Revised in the eng review (D13):
  `docker/production/docker-compose.yml` pulls the upstream
  `openemr/openemr:latest` image, which does not contain this fork's
  module, so "production compose unchanged" cannot ship it. The agent
  ships to the same box, satisfying the PRD's same-infra rule. A custom
  image is tracked in TODOS.md.

## Validation Spike: What Is Already Known vs. What Still Runs

Static inspection of the service layer resolved most of premise #4 before
any script ran:

- **Service reads enforce no authorization.** `PrescriptionService`,
  `AllergyIntoleranceService`, and `BaseService` contain zero
  `AclMain` calls. `EncounterService` has two, both in the *update* path
  (`src/Services/EncounterService.php:450-455`); its `search()` and read
  methods check nothing. Conclusion: authorization is the caller's job.
  **The tool layer must call `AclMain::aclCheckCore()` before every
  service call** — at minimum `('patients','med')` for medications and
  allergies, `('encounters','notes')` for encounters, plus the per-row
  `('sensitivities', $row['sensitivity'])` check that line 450 applies on
  update but reads skip. This is the minimal authz the subagent's
  contingency called for; it is now a required part of step 2, not a
  fallback.
- **The facility-ID mismatch does not drop rows.** The facility join in
  `EncounterService` is a `LEFT JOIN` (line 309), so the 99.8% of
  encounters with a nonexistent `facility_id` still return, with null
  facility columns. The fact assembler treats facility name as optional.
  No known-good-patient-subset fallback is needed for this reason.

What the runtime spike still has to do, against 5-10 seed patients:
1. Time the full fact-assembly round trip (all three services + ACL
   checks) against the 5-second latency budget.
2. Inspect encounter data quality for the "since last visit" boundary:
   how many patients have a usable prior encounter, and whether encounter
   dates/status are consistent enough to pick one deterministically.
3. Confirm a non-admin user with restricted ACLs is actually refused by the
   tool-layer checks above (positive and negative test).

## Success Criteria (Wednesday, each falsifiable)

1. **Deployed:** the public URL loads OpenEMR, `admin`/`pass` logs in, and
   opening any seeded patient's chart auto-opens the briefing panel.
2. **Works across patients:** for 10 named seed patients (list them in the
   eval dataset), the briefing renders with zero `[unverified — removed]`
   markers and zero "unable to verify" fallbacks. Any patient that fails
   is listed in the submission as a known limitation, not hidden.
3. **Verifier is real:** the eval suite includes at least 3 adversarial
   cases where the LLM output is *forced* to contain a wrong value, an
   uncited sentence, and a nonexistent fact ID — and all three are stripped
   by the verifier. Unit tests pass for the verifier and the normalization
   rules.
4. **Omission guard is real:** for at least one seed patient with a new
   allergy or new medication since the prior encounter, the LLM prompt is
   deliberately instructed to omit it, and it still appears in the "Also on
   file since last visit" section.
5. **Authorization is real:** a user without `patients`/`med` ACL is
   refused by the tool layer (negative test), and `admin` is not (positive
   test).
6. **Multi-turn works:** on any of the 10 patients, one follow-up question
   ("when was that started?" or similar) returns an answer whose every
   value carries a fact ID and survives the verifier.
7. **Latency:** p50 chart-open-to-rendered-briefing under 5s across the 10
   patients, measured and recorded.
8. **Observability:** every request above has a correlation ID visible in
   the logs with per-step timing and token counts.

Anything not met by submission time is stated as a known gap in the
submission rather than left for a grader to discover.

### Data flow

```
chart page load (PatientDemographics RenderEvent)
        │
        ▼
 panel JS ── POST chat.php {csrf, facts_hash?, transcript[]}
        │
        ▼
 chat.php: session ▸ CSRF ▸ pid=$_SESSION ▸ ACL(patients/med, encounters/notes)
        │
        ▼
 FactAssembler(pid, currentEncounter)
   ├─ prior encounter (6A) ──────────────┐
   ├─ EncounterService  (date-bounded, sensitivity-filtered)
   ├─ ObservationLabService (date-bounded, abnormal, sensitivity)
   ├─ PrescriptionService (current list; changes vs prior)
   ├─ AllergyIntoleranceService (current list; vs drugs → allergy_hit)
   ├─ ConditionService (new problems)
   ├─ computed facts: deltas, "new since", "N more not shown"
   └─ strip identifiers ─► FactSet{facts[id→…], facts_hash}
        │
        ├──────────────► render fact table (no LLM)  ──► panel (instant)
        │
        ▼
 NarrationPipeline(mode=briefing|followup)
   ├─ cache lookup (facts_hash, PROMPT_VERSION, model) ─hit─► narration
   ├─ OpenAiClient (Structured Outputs; typed failures; 1 retry)
   ├─ Verifier(narration, FactSet)      strip + mark
   ├─ OmissionGuard (briefing only)     append "Also on file"
   └─ cache store ─► narration + status ─► panel (async)
        │
        ▼
 Monolog processor (correlation id) ─► syslog + Langfuse Cloud trace
```
